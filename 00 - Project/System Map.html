Workbench System Map

state as of 2026⁠-⁠09⁠-⁠01

The Emerson Workbench replaces drift-prone 100–300 slide PowerPoint decks with a maintained, source-linked course system. It is built in four layers; the one under active construction is the Pipeline Console — the tool that runs a legacy course through five inspection stages and produces a finished course package, with a person signing off at every gate.

01  /  Architecture

Four layers, built bottom-up

Each layer plugs into the one below it. The Console produces a Cartridge; a Cartridge loads into a Workshop; a Workshop lives in the Home.

1 Workbench (Home) not started Top-level landing for every Educational Services course; departmental branding and ownership.
2 Workshop (Course Shell) built · frozen The reusable course layout: navigation, day/chapter/module hierarchy, the four slide templates, context pane, presenter mode. Structurally locked in. Proven against all of 1400 Chapter 2. Remaining work is finishing content, not changing structure.
3 Cartridge not split off The content package for one course — the Pipeline's output — that plugs into a Workshop. Cartridge content and Workshop shell are still edited together in live nav. Formal separation is deferred until after the Console.
4 Pipeline Console active build The tool that runs a legacy PowerPoint course through the five pipeline stages and produces a Cartridge. Its own repository, sibling of the vault. Build phases 0–6 complete. Running on real 1400 content now. Only multi-project hardening remains.
02  /  The pipeline

Five stages, in fixed order

Each course chapter moves through the stages as its own state machine. Stage 0 (bulk convert) is course-wide; Stages 1–4 run per chapter.

StageWhat it doesOwnerHow provable
0 Bulk convert Source .pptx → HTML slides + manifest + conversion report. script Fully. Deterministic, no judgement.
1 Cut the arc Group slides into days → chapters → modules; boundaries from each module's objective, not deck order. AI cut → human approve Structure is checkable; the cut is editorial judgement.
2 Author context Per module: a doing-centred objective and 4–6 source-checked key concepts. AI draft → human approve Page refs are checkable; fidelity to source is judgement.
3 Four-part pass Re-sequence, source cross-check, consolidate split slides, apply templates, polish. AI rework → human review, per slide Render checks are automated; callouts, image choice, polish are judgement.
4 Verify & publish Whole-deck render + integrity checks; regenerate data; publishable Cartridge. script + human Mostly. One verify.ps1 pass.

04  /  The console

A control panel, not a dashboard

6 build phases done 67 tests 16 commits 5 pipeline stages wired
  • Separate app Its own Electron repository, sibling of the vault. It drives Claude Code with the vault as the working directory, so the pipeline docs, memories, and Source Library are all in context — but the Console's code is never mixed into course content.
  • Instrument feel Chunky stage switches, indicator lights, a monospace instrument readout. Colour carries live status. Built to feel like operating a physical process-control panel, the domain adjacent to valve work — not a generic web dashboard.
  • Before / after At Stage 1 and 2, the review rack shows what the cut or the authored context produced next to an outline of what the source slides actually cover. At Stage 3, a real before/after screenshot of each slide. The human approves knowing exactly what changed — never a black box.
  • Per-chapter Each chapter carries its own Stage 1–4 state; switching the target chapter re-derives the panel from that chapter's real progress. Stage 0 (bulk convert) is course-wide.
05  /  The vault

Where everything lives

One Obsidian vault, six top-level folders. The Console's own code is not among them.

00 - Project

Charter, roadmap, architecture, this map, open questions, glossary.

10 - Courses

One folder per course — content, instructor/student guides, the built Presentation/, the source deck.

20 - Source Library

Control Valve Handbook, Fisher manuals, technical publications — the primary sources courses cite.

30 - Templates

Obsidian note skeletons: Bench Book, Bench Notes, Course Home, Source Document.

40 - Engine

The shared course runtime: design system, deck runner, learning shell, slide templates, the PPT→HTML generator, verify.ps1, headless render checks.

99 - Attachments

PDFs, images, exported decks.
